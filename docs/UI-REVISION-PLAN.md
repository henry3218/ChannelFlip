# Channel Flip 介面與操作流程修正計畫

日期：2026-09-12  
狀態：五項問題已實作修正；測試證據及尚待人工驗收的範圍見 [驗證紀錄](../VALIDATION.md)。  
範圍：使用者提供的五項介面審核問題。Windows 10 環境與相容性測試暫不納入本輪。

後續 2.1.1 修正：完成已確認後閒置的獨立文案、滑塊開關、輔助工具切換事件，以及實測發現的 Windows 文字大小同步問題。Windows 設定、跨實體螢幕、Narrator 與耳機重連的各項進度，另列於驗證紀錄；模擬畫面不作為實體驗收的替代證據。

## 目標與現況依據

使用者應能清楚知道正在操作哪個裝置、互換設定是否開啟、目前是否偵測到核心處理，以及系統操作會影響哪些裝置。

保留目前集中的功能、深色與薄荷綠視覺、來源到左右耳的映射、原生音訊核心及備份還原能力。沿用 WPF 與單一 EXE 發佈方式、MIT 授權。

規劃時已對照原始碼，並以使用者提供的八個狀態／尺寸畫面審核作為需求依據。以下保留原修正與驗收計畫；實作後的結果另記錄於驗證紀錄。

| 審核問題 | 目前程式依據 | 修正階段 |
| --- | --- | --- |
| 開關開啟被當成運作正常；無裝置提示失配 | `src/MainWindow.cs` 的 `UpdateState()` 主要使用 `Attached && Enabled`；一般提示缺少完整狀態覆蓋 | 第一階段 |
| 全裝置移除與普通功能並排 | `RemoveEngine` 直接呼叫 `Engine.Remove()`；`ResetAll`、`DeviceSetup` 也含跨裝置操作 | 第二階段 |
| 裝置消失後換成清單第一項 | `Refresh()` 使用 `FirstOrDefault(...) ?? list.FirstOrDefault()` | 第一階段 |
| 首次設定與日常操作混用 | `Toggle`、`SetupAction`、未設定時的 `DeviceSetup` 都進入 `Toggle()` | 第二階段 |
| 元件、字級、縮放及高對比不完整 | `MainWindow.xaml` 使用系統預設 ComboBox、多處 11–12 DIP 與整頁捲動；預覽固定為 660 × 930、96 DPI | 第三階段 |

## 第一階段：可信的狀態與穩定的操作目標

### 1. 分開設定、運作觀察與聽感驗證

主卡固定表達三種不同資訊：

- **互換設定**：開啟、關閉、未設定或無法讀取。只有讀取成功才呈現開／關。
- **運作狀態**：依目前裝置與新取得的處理證據判定，不能由設定值推定。
- **方向測試**：記錄本次測試有無偵測到處理；實際左右耳方向由使用者聽音確認。

映射文字標為「設定方向」或「預期方向」。錯誤、離線、待驗證時仍可說明設定意圖，但不得把箭頭或綠色徽章當成運作成功證據。薄荷綠主操作色可以保留，成功狀態另以文字與圖示辨識。

| 情境 | 運作狀態文案方向 | 操作與提示 |
| --- | --- | --- |
| 沒有可用裝置，也沒有已保存目標 | 尚無輸出裝置 | 提示連接裝置／重新整理；停用設定與測試 |
| 已保存的指定裝置不在線上 | 裝置已離線 | 保留名稱與設定；提示重新連接或手動選擇其他裝置 |
| 讀取裝置或核心狀態失敗 | 無法取得狀態 | 提供重試與可展開的錯誤詳情；設定值顯示未知 |
| 少於兩聲道或無法取得必要格式 | 此裝置目前無法使用左右互換 | 說明實際原因；停用不能執行的動作 |
| 裝置可用，尚未接入核心 | 尚未設定 | 主操作為「設定此裝置」；可播放原始方向測試音 |
| 正在設定、切換、測試或移除 | 正在執行具體操作 | 顯示鎖定的目標名稱與進度；阻止重複命令 |
| 核心回報錯誤 | 核心異常 | 錯誤優先顯示；提供重新檢查及進階復原入口 |
| 裝置音效強化被停用 | 音效強化已關閉 | 提供 Windows 音效入口，說明互換可能無法套用 |
| 已設定，但沒有近期處理證據 | 等待音訊／尚待測試 | 提供測試鍵；沒有播放音訊本身不判為故障 |
| 設定開啟且偵測到新的互換處理 | 已偵測到互換處理 | 顯示近期觀察；仍保留耳機方向測試 |
| 設定關閉 | 互換已關閉 | 清楚顯示設定方向為原方向；處理觀察可另外呈現 |
| 剛播放測試音，卻沒偵測到應有處理 | 本次測試未偵測到互換 | 顯示可操作的排查步驟；不回到綠色成功提示 |

狀態判定規則：

1. 使用同一端點、同一觀察期間的 `Frames`／`SwappedFrames` 增量判定近期處理。單次讀取到累積值大於零、`Loads` 大於零或舊 PID，都不構成目前生效證據。
2. 初步採兩個更新週期作為近期觀察範圍，實作時依既有四秒更新節奏驗證。超過範圍回到「等待音訊」，保留標明時間的上次測試結果。
3. 裝置切換、斷線、音訊宿主重啟、計數重設或設定改變，會使相關驗證失效；不能沿用上一個裝置或上一輪開關的成功狀態。
4. 錯誤、離線與無法讀取優先於開關顏色及歷史成功。一般重新整理不得清除尚未解決的測試失敗。
5. 測試完成、測試取消、核心處理通過、使用者聽感確認分別記錄。失敗與取消不顯示成功訊息，也不能把計數通過寫成「已確認右耳出聲」。
6. 依動作能力判定可用性：離線時禁止對該裝置播放音訊；核心異常但設定仍可讀寫時，仍允許關閉已開啟的互換。

### 2. 裝置選取行為

預設採「固定裝置」，保存端點 ID 與最後已知名稱；相同名稱的不同端點不能互相替代。既有 `device.txt` 遷移為固定裝置偏好；目標離線時仍保留它。

首次使用尚無保存目標時，可預選系統多媒體預設裝置供使用者查看；若無預設，則要求選擇裝置。單純預選不會啟用互換。

提供兩個明確選項：

| 選取方式 | 系統預設改變時 | 原裝置斷線時 |
| --- | --- | --- |
| 固定裝置（預設） | 保持原目標 | 保留離線項目；重新連接相同端點後恢復顯示 |
| 跟隨系統預設 | 主視窗的操作及測試目標跟隨 Windows 多媒體預設裝置 | 改為目前預設；若不存在，顯示沒有預設裝置 |

「跟隨」是介面的目標選取方式。各裝置的設定獨立保存，新裝置先顯示「尚未設定」，再由使用者設定。切換目標時會清楚提示，並清除上一個目標的即時觀察。視窗關閉期間，各已設定裝置保留其互換設定；下次開啟再解析系統預設。本輪不增加常駐背景自動替新裝置設定的機制。

開始設定、播放測試或切換開關時，先固定該次命令的端點 ID；執行前再次確認可用性。操作途中預設改變或裝置斷線，只能讓原操作完成或明確失敗，不得把命令重新導向別的裝置。完成後才更新跟隨目標，舊結果不得覆蓋新目標的狀態。

四秒重新整理只更新必要資料；保留鍵盤焦點、開啟的下拉選單和使用者正在進行的選擇。

**階段驗收門檻**：設定開啟加上核心錯誤不會顯示成功；無裝置不出現要求按停用測試鍵的提示；固定裝置斷線不改選其他裝置；重啟程式仍遵守同一選取方式；每次操作只作用於啟動當下指定的端點。

## 第二階段：首次設定、日常使用與進階操作

### 3. 主畫面只保留一條主要流程

主畫面順序定為：裝置與選取方式 → 設定開關與運作狀態 → 預期左右映射 → 左／右測試 → 結果及必要提示。使用說明、Windows 音效及進階設定保留容易找到的入口。

首次使用：

1. 選取裝置後，主操作顯示「設定此裝置」。合併目前三個重複設定入口。
2. 展開一次設定說明，列出目標名稱、裝置設定變更、整台電腦音訊服務會短暫中斷，以及目前未簽章版本所需的系統層級設定。
3. 確認按鈕命名「設定並開啟互換」，使完成後的行為明確；接續既有 Windows 管理員授權與備份流程。
4. 設定成功後轉入日常控制，顯示左右測試；回報核心測試結果，邀請使用者確認實際方向。
5. 取消授權、設定失敗及部分還原各有結果；重讀狀態後顯示實際完成範圍。

日常使用：

- 固定標籤「左右互換」配清楚的開／關控制；狀態文案不兼任安裝入口。
- 左右測試緊鄰主控制；依目前開關顯示應從哪隻耳朵聽到。
- 「設定已保存」與「近期偵測到處理」分別表達。核心錯誤時不宣稱關閉視窗仍能正常互換。
- 一般開關只修改該裝置的互換設定，不經過首次設定說明或管理員流程。

### 4. 系統操作集中於「進階設定」

| 操作名稱 | 影響範圍與執行前說明 |
| --- | --- |
| 重新啟動電腦音訊服務 | 整台電腦音訊可能短暫中斷；替代容易誤認為只操作當前耳機的「重新載入核心」 |
| 關閉所有已設定裝置的互換 | 列出本程式已設定的裝置；保留核心、備份及音訊宿主設定 |
| 移除所有裝置的設定 | 明示「本程式已接入的所有裝置」，包含目前離線的裝置；列出清單／數量、還原內容，以及全系統音訊中斷 |

移除流程使用專用確認畫面，明確區分「關閉互換」與「還原並移除設定」。預設焦點為取消，確認後才啟動管理員操作。若確認後影響清單改變，先重新顯示範圍。

移除結果依重新讀取的裝置登記、備份與宿主設定呈現；部分失敗或保留了外部修改時說明未完成項目，不能只因子程序結束就宣稱全部還原。錯誤詳情可複製，主畫面保留簡短的下一步。

進階功能依全體已設定裝置判定可用性，即使目前選取裝置離線仍能找到全域關閉與移除入口。

**階段驗收門檻**：首次設定只有一個入口；一般互換不觸發安裝流程；取消確認不修改設定；進階畫面揭露的範圍與實際命令一致；部分失敗不顯示全成功。

## 第三階段：一致元件、易讀文字與尺寸適應

1. 統一下拉選單、選項、按鈕、提示、焦點與停用樣式。下拉選單包含滑鼠、鍵盤、已選取及展開狀態。
2. 狀態、裝置名稱、操作影響與主要說明以 14–16 DIP 為起點，實際依排版驗收；輔助文字至少 13 DIP。這是本專案設計目標，並非宣稱取得無障礙認證。
3. 調整卡片高度與邊距，把測試鍵移入主操作區。首次設定長說明採獨立畫面，避免把測試鍵推到主畫面下方。
4. 一般尺寸 680 × 900 DIP 與最小視窗 600 × 640 DIP 都能看到裝置、主操作、主要狀態及左右測試。長裝置名稱與錯誤詳情可以換行／展開，完整內容可取得。
5. 若實際工作區小於最小尺寸，提供可操作的緊湊／捲動退路，避免視窗底部落在螢幕外；不以縮小重要文字解決。
6. 高對比時使用成對的系統前景／背景色及可見邊框；狀態同時包含文字、圖示，不依賴顏色。WPF 系統主題資源使用動態參照以回應系統變化，依據 [Microsoft WPF 資源說明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/systems/xaml-resources-overview) 與 [Windows 高對比指引](https://learn.microsoft.com/zh-tw/windows/compatibility/high-contrast-mode)。
7. 完成 Tab 順序、方向鍵選取、Enter／Space 操作、Esc 關閉次要視窗、焦點還原及控制項可存取名稱。依據 [Microsoft WPF 焦點機制](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/focus-overview)，同時實測鍵盤操作與螢幕閱讀器讀出的名稱／狀態。
8. 檢查 manifest、執行階段及實際跨螢幕縮放行為。100%、125%、150%、200% 縮放列入驗收；圖片放大只能輔助排版檢查，不能代替真正的 DPI 測試。

**階段驗收門檻**：重要操作沒有遮蔽、重疊或被截斷；小視窗可直接看到主操作與測試；高對比下文字、選取與焦點仍可辨識；只用鍵盤可完成選裝置、互換與測試。

## 實作安排與驗證

| 順序 | 預計修改處 | 完成證據 |
| --- | --- | --- |
| 1 | 新增獨立的狀態判定與裝置選取模型；`MainWindow.cs` 接收狀態結果；偏好保存／遷移 | 可注入模擬資料的狀態及選取測試 |
| 2 | `MainWindow.cs` 的首次設定、日常控制、進階操作及結果處理；必要的 `Engine.cs` 結果讀取 | 命令目標／影響範圍測試、取消及部分失敗檢查 |
| 3 | `MainWindow.xaml` 及必要的子視窗／樣式資源、DPI 設定 | 各狀態與尺寸畫面、鍵盤及高對比實測 |
| 4 | 測試情境入口與渲染工具；`tests`、既有打包驗證工具 | 自動測試紀錄與畫面矩陣 |
| 5 | `README.md`、`FIRST_RUN.md`、使用說明、`VALIDATION.md` | 與畫面一致的名稱、作用範圍及已驗證項目；本機預覽 EXE／ZIP |

模擬狀態模式須注入資料並攔截系統命令，不讀寫真實裝置設定、不播放真實音訊。預覽尺寸、DPI 與情境可指定；正式模式與模擬模式共用狀態判定及畫面呈現，避免測試的是另一套介面。

核心驗證案例至少包含：

- 無裝置、尚未設定、已關閉、已開啟但待驗證、正在處理、核心錯誤、狀態讀取失敗、音效強化停用、裝置離線、忙碌及部分失敗。
- 有歷史處理計數但目前無音訊、宿主重啟、計數倒退或重設、測試失敗後的一般重新整理。
- 固定裝置斷線重連、同名不同 ID、系統預設改變、操作中斷線或預設切換、重新開啟程式後偏好保留。
- 首次授權取消、移除取消、確認清單改變、全域操作包含離線裝置、命令結果不完整。
- 最小／一般尺寸、長名稱與長錯誤、100%／125%／150%／200% DPI、高對比、鍵盤與焦點。先將狀態與兩種尺寸交叉驗證，再對最容易溢出的情境擴充 DPI 與主題組合。

完成介面實作後執行既有 C#、原生 COM／DSP 與單一 EXE 驗證；新增測試聚焦狀態、命令範圍及裝置選取的行為。既有 `VALIDATION.md` 記錄 2.0.1 的 62 項 C# 與 52 項原生測試通過，本輪規劃並未重跑，也不把舊紀錄當成新版通過證據。

最後在目前 Windows 11 與 MOMENTUM 4 上檢查新版的一般開／關、來源左右測試、關閉／重開視窗及斷線重連。裝置處理計數與使用者聽感分別記錄。涉及移除／重新設定的驗收安排獨立時段，按既有備份機制保留並恢復測試前設定；不為截取 UI 畫面反覆改動系統。

## 完成定義

五項問題各自通過對應驗收，才將本輪標示完成。交付修正後的本機預覽版、前後畫面、測試結果與更新說明。無法取得實測證據的項目清楚列為待驗證；本輪不宣稱 Windows 10 已驗證、產品已取得認證，或已發佈至 GitHub。
